## Special checks

1. **Is ownership stored/handled separately from staff permissions? Can a restaurant have multiple owners? — No implementation found.** There is no ownership membership model, staff model, invitation workflow, or Laravel code. The only owner record is a single mock profile in `src/services/ownerService.js`.
2. **Does the backend verify restaurant membership and specific permissions on every restaurant endpoint? Can owner A access restaurant B's data? — No enforcement exists in this repository; isolation cannot be established.** There are no backend endpoints or policies. The owner UI uses one localStorage-backed mock restaurant and unscoped local list updates. The owner routes in `src/App.jsx` are not wrapped in the frontend `ProtectedRoute`; frontend checks would not substitute for backend authorization.
3. **Is the sidebar filtered by backend-confirmed permissions? — No.** `src/layouts/OwnerLayout.jsx` supplies a fixed six-item navigation array and does not request permissions or filter by them.
4. **Are Activity Logs written by the backend for §14 actions? — No implementation found.** No backend source, activity model/service/route, or tests exist.
5. **Do menu/profile changes appear on the customer-facing restaurant page through a shared source? — No.** Owner edits use `salo_owner_*` localStorage keys through `src/services/ownerService.js`; customer restaurant data comes from separate `INITIAL_RESTAURANTS` fixtures/API fallback in `src/services/customerService.js`. No owner API or shared persistence connects them.
6. **Files using mock/hardcoded business data, local fallback, or browser storage for business data/credentials:**
   - Owner surface: `src/services/ownerService.js`; `src/layouts/OwnerLayout.jsx` (fixed navigation and notification count); `src/features/restaurant/pages/OwnerDashboard.jsx`; `src/features/restaurant/pages/OwnerProfilePage.jsx`; `src/features/restaurant/pages/OwnerMenuPage.jsx`; `src/features/restaurant/pages/OwnerOrdersPage.jsx`; `src/features/restaurant/pages/OwnerReservationsPage.jsx`; `src/features/restaurant/pages/OwnerEarningsPage.jsx` (includes hardcoded settlement rows and payout destination).
   - Other business fixtures/local state: `src/services/customerService.js`; `src/contexts/CartContext.jsx`; `src/services/adminService.js`; `src/services/riderService.js`; `src/features/customer/pages/PartnerApplicationPage.jsx`.
   - Authentication/token handling: `src/services/authService.js` (demo users and offline auth fallbacks); `src/features/auth/pages/LoginPage.jsx` (demo password prefill); `src/services/apiClient.js` (reads/writes bearer token); `src/contexts/AuthContext.jsx` (stores user profile).
   - Development-only UI examples: `src/features/showcase/DesignShowcase.jsx`. `src/contexts/ThemeContext.jsx` stores only the display theme and is not business/credential data.
7. **Any password, token, or secret in browser storage? — Token: yes. Password/other secret: no storage write found.** `src/services/authService.js` and `src/services/apiClient.js` persist the token in localStorage key `salo_token`; offline login stores synthetic demo tokens there. `salo_user` stores the user object. `src/features/auth/pages/LoginPage.jsx` contains a `password123` demo prefill in source, but the reviewed code does not persist the password to localStorage/sessionStorage. No sessionStorage use was found.
